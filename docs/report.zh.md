# `dsh-harness-router` 汇报文档

> 一句话：让同一个 Agent 在收到任务的第一时间，自动切换到最适合这类任务的提示词和工具配置。

## 1. 为什么做这个插件

现在大多数 Agent Harness 对所有任务使用同一套运行配置：同一段系统提示词、同一组工具、同一套规划要求。但任务类型差异很大：

- 简单问答被要求先写 todo、先做计划，浪费步骤
- 需求模糊时直接开工，做到一半才发现方向不对
- 复杂重构没有强制拆分和验收，容易漏需求、跳步骤

结果是**需求识别偏差、任务拆分不稳定、步骤和成本浪费**。

已有社区方案各有侧重：`dsh-routing-suite` 偏重工具渐进披露和阶段闯关；`dsh-help-me-to-ask` 只解决需求澄清；`dsh-harness2` 是成本较高的离线自优化闭环。我们需要的是一层**轻量、可解释、可记录、可关闭**的运行时路由。

## 2. 插件做了什么

`dsh-harness-router` 是一个 DSH 插件。它在**每个会话的第一条真实用户消息**上做一次分类，然后在**首次模型请求组装之前**套用对应的 Harness 配置。

```
用户第一条消息
      │
      ▼
agent/inbox/claimed        （工具解析和提示词组装之前）
      │
      ▼
规则分类器                  direct / clarify / decompose / balanced
      │
      ├─ 注入当前会话的提示词引导
      ├─ 应用工具 allow / deny
      └─ 写入一条路由决策日志
      │
      ▼
首次模型请求已经使用路由后的配置
```

它不修改 Agent 循环，不替换模型，也不侵入 DSH 核心；所有注册都随插件和会话卸载而清理。

## 3. 四条路由

| 路由 | 适用任务 | 提示词引导 | 工具策略 |
|---|---|---|---|
| `clarify` | 需求模糊、缺少关键约束 | 复述目标、列假设和高影响歧义，最多问两个关键问题 | 不额外限制 |
| `decompose` | 重构、迁移、调试、端到端等多步骤任务 | 提取验收条件，先写 3–7 步 todo，再逐步验证 | 不额外限制 |
| `direct` | 简短的事实/解释类问题 | 直接回答，不引入计划机制 | 禁用 `todo_write`、`exit_plan_mode` |
| `balanced` | 没有明显信号 | 保持现有配置不变 | 不变 |

分类器是确定性的、可解释的：按关键词命中、文本长度、子句数打分，记录命中的词和置信度。**不额外调用模型，不增加 API 成本。**

实际例子：

- `dsh 是什么？` → `direct`
- `帮我优化一下这个页面` → `clarify`
- `重构用户模块，拆分 service 和 UI，补测试然后跑全量回归` → `decompose`
- 没有明显信号 → `balanced`

## 4. 它到底有什么用

### 对使用者

- 不用手动切换模式：插件根据任务自动选择
- 简单任务少做无用规划，复杂任务先拆分再执行
- 模糊任务先澄清，减少“做完才发现不对”
- 任何时候可以用 `/route` 查看、切换或关闭

### 对研究

- 把“提示词、工具配置”从固定配置变成**可按任务路由的自变量**
- 路由决策逐条落盘，带会话、置信度、命中词和配置哈希，实验可复现
- 为后续 A/B 评估提供基础：同一批任务、同一模型，对比路由前后需求识别和任务拆分质量
- 可以和澄清卡片（`dsh-help-me-to-ask`）、自优化闭环（`dsh-harness2`）组合

### 对工程

- 基于 MIT 许可的社区实现改写，保留 LICENSE / NOTICE 归属
- 按 DSH 0.2.x 的 bundle 格式重新打包，安装即用
- 纯 ESM，无构建步骤；有单测和真实装配验证
- 可以继续发布到 DSH 插件市场

## 5. 已经验证了什么

| 项目 | 状态 |
|---|---|
| 分类器与路由规则 | 12 个单元测试全部通过 |
| 首轮生效时机 | 用 DSH 官方 agent-loop testkit 验证：首条消息 claim 时提示词段落已注册 |
| Web 运行时加载 | 已安装进 web profile，Web UI「已安装插件」中可见且启用 |
| 决策日志 | 路由时写入 `~/.dsh/harness-router/decisions.jsonl` |

### 还没验证什么

- 还没有用真实模型跑完整会话对比（当前 UI 尚未配置 API Key）
- 还没有量化“路由后需求识别/任务拆分提升了多少”
- 规则分类在真实任务集上的准确率尚未测量

汇报时需要明确：**目前验证的是机制可用，不是效果已证明。** 下一步才是效果评估。

## 6. 五分钟演示脚本

1. 打开 Web UI，添加 API Key，选择工作区
2. 新建会话，依次输入：
   - `dsh 里的 plugin 和 preset 有什么区别？` → 预期 `direct`
   - `帮我优化一下这个页面，看着有点乱` → 预期 `clarify`
   - `重构用户模块，拆分 service 和 UI，补测试，然后跑全量回归` → 预期 `decompose`
3. 输入 `/route`，展示当前路由和命中原因
4. 终端执行 `tail -f ~/.dsh/harness-router/decisions.jsonl`，展示决策记录
5. 输入 `/route off`，演示可以随时关闭

## 7. 和现有方案的关系

| 方案 | 它做什么 | 我们的差异 |
|---|---|---|
| `dsh-routing-suite` | 任务感知路由 + 工具渐进披露 + 阶段闯关 | 我们复用了它的路由核心和 hook，但去掉重型阶段机制，聚焦需求识别与拆分，适配 DSH 0.2.x |
| `dsh-help-me-to-ask` | 首条消息弹卡澄清，生成任务说明 | 我们覆盖澄清、拆分、直答三类路由，并同时调整工具策略；后续可把它的卡片并入 `clarify` |
| `dsh-harness2` | 离线跑任务、提议并 probe 更好的 Harness | 我们是运行时轻量路由，成本低；两者可以组合：用它做离线优化，用我们做在线生效 |

## 9. 可能被问到的问题

**Q：这不就是给模型加提示词吗？**
A：不只是。它在首轮模型请求之前同时改变提示词和工具可用集，且按任务自动选择、可配置、可记录、可人工覆盖、可关闭。

**Q：规则分类准不准？**
A：当前是确定性的关键词/长度/结构打分，透明可解释，词表和阈值都可配置。误判时可以用 `/route` 手动覆盖。后续会加 LLM 兜底。

**Q：会不会限制模型能力？**
A：默认 `balanced` 完全不改配置；`direct` 只禁用计划类工具，不影响读写、搜索、终端等执行能力。随时可以 `/route off`。

**Q：和 plan mode / preset 有什么区别？**
A：plan mode 是用户显式进入的单一模式；preset 是会话创建时选的一套完整 Agent 组合。本插件是运行时按任务自动选择轻量提示词/工具策略，不要求用户预先选择，也不替换整个 preset。

**Q：怎么证明它有效？**
A：目前还没有效果数据。下一步会用同一批任务和模型做配对实验，比较路由前后的完成率、澄清行为、拆分质量和步骤成本。这是插件设计时就预留的评估路径。

**Q：会增加成本和延迟吗？**
A：分类是本地纯规则，不调用模型；唯一的成本变化是路由注入的提示词会略微改变输入长度。工具限制反而可能减少无效步骤。

**Q：会记录隐私数据吗？**
A：决策日志只记录 160 字符预览、长度和配置哈希，不记录完整用户文本；日志路径可配置，也可以关闭。

**Q：为什么基于别人的项目？**
A：`dsh-routing-suite` 已经验证了 `agent/inbox/claimed` 首轮路由的可行性，MIT 许可允许改写。我们保留归属，去掉不兼容的重型机制，按 0.2.x 重新打包，避免重复造轮子。

## 10. 一页结论

`dsh-harness-router` 把 Harness 从“一套配置服务所有任务”变成“按任务自动选择提示词和工具策略”。它已经完成机制验证和运行时安装，下一步是用配对实验回答“需求识别和任务拆分是否真的更准确”。如果这个结论成立，它可以作为 Harness 运行时优化的一个低成本、可解释、可复用的基础组件。
